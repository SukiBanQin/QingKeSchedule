# 课表软件 Web MVP 技术方案

## 1. 文档目的

本文档依据[产品设计文档](./product-design.md)，明确课表软件 Web MVP 的技术选型、模块边界、核心数据结构、质量保障方式和后续演进路径，作为后续开发与评审的共同基线。

本文档聚焦技术方向，不展开组件视觉稿、接口逐字段定义和具体任务拆分。

## 2. 方案结论

MVP 采用纯前端单页应用，不建设后端服务。推荐技术组合如下：

- **Vue 3**：构建页面、表单和可复用组件。
- **TypeScript**：描述课程模型并实现教学周、单双周和冲突检测等规则。
- **Vite**：提供本地开发、构建和静态资源打包能力。
- **Vue Router**：管理周课表、今日课程、课程编辑和学期设置页面。
- **Composition API**：管理跨页面共享的响应式状态，MVP 暂不引入 Pinia。
- **原生 CSS、CSS Grid 与 CSS Variables**：完成课表网格、响应式布局和颜色系统。
- **localStorage**：持久化当前学期和课程数据，并通过独立存储层隔离具体实现。
- **Vitest、Vue Test Utils 与 Playwright**：分别覆盖业务规则、组件交互和核心用户流程。

最终产物是一组静态文件，可部署到任意静态托管服务。所有用户数据仅保存在当前浏览器，不会发送到服务器。

## 3. 技术目标与约束

### 3.1 技术目标

- 正确实现教学周、每周/单周/双周、多上课安排和时间冲突等核心规则。
- 保持页面状态一致，课程修改后周课表和今日课程立即更新。
- 刷新或重新打开浏览器后恢复完整数据。
- 让业务规则与 Vue 页面、浏览器存储解耦，以便单独测试和在未来复用。
- 支持主流现代桌面浏览器，并保证手机浏览器上的基础可用性。
- 控制首版依赖数量和工程复杂度，为后续迭代保留清晰边界。

### 3.2 本阶段不解决的问题

- 不设计账号、云同步和服务端数据库。
- 不实现系统通知、后台任务和教务系统接入。
- 不为搜索引擎优化或服务端渲染引入 Nuxt。
- 不提前构建手机 App、桌面客户端或微服务。
- 不在 MVP 阶段引入 IndexedDB、PWA 和复杂状态管理框架。

## 4. 总体架构

应用按职责分为四层，依赖方向从界面层指向基础设施抽象，核心业务规则不依赖 Vue 或浏览器 API。

```text
页面与组件（views / components）
             ↓
应用状态与用例（composables / application）
             ↓
领域模型与业务规则（domain）
             ↓
存储接口及浏览器实现（repositories / storage）
```

### 4.1 页面与组件层

负责页面布局、表单输入、错误提示和用户交互。课表网格、课程卡片、课程表单、确认弹窗等拆分为可复用组件。组件不直接读写 `localStorage`，也不自行计算复杂教学周规则。

### 4.2 应用状态与用例层

使用 Composition API 建立一个应用级课表状态入口，负责：

- 启动时读取并初始化本地数据。
- 对页面暴露当前学期、课程列表和派生视图。
- 协调新增、修改、删除课程及保存结果。
- 将存储错误转换为用户可理解的提示。

MVP 状态规模有限，不引入 Pinia。若后续出现账号、多学期、云端缓存等复杂状态，再评估迁移。

### 4.3 领域层

使用不依赖 Vue 的纯 TypeScript 类型和函数实现：

- 当前教学周计算。
- 某个安排在指定教学周是否生效。
- 指定日期的课程筛选和排序。
- 已结束、进行中、未开始状态计算。
- 节次范围、周次范围和单双周交集的冲突检测。
- 学期、节次和课程表单的业务校验。

纯函数便于单元测试，也能在未来的手机 App 或服务端中复用。

### 4.4 基础设施层

定义课表数据仓库接口，并由 `localStorage` 提供首个实现。页面和领域层只依赖仓库接口，不依赖具体存储介质。后续切换 IndexedDB 或远程 API 时，可以保留上层调用方式。

## 5. 前端工程结构

建议在开始开发时采用以下目录边界：

```text
src/
  app/                 # 应用入口、路由和全局样式
  views/               # 周课表、今日课程、课程编辑、学期设置
  components/          # 通用组件和课表专用组件
  composables/         # 应用状态及页面可复用交互逻辑
  domain/              # 类型、校验和纯业务规则
  repositories/        # 数据仓库接口
  storage/             # localStorage 实现、迁移与恢复
  utils/               # 无业务含义的通用辅助函数
tests/
  unit/                # 领域规则和组件测试
  e2e/                 # Playwright 核心流程测试
```

目录只表达稳定职责，不按每一个小功能建立过多抽象。只有被复用或具有独立业务含义的逻辑才从组件中提取。

## 6. 核心数据模型

数据使用 TypeScript 接口表达。日期统一存储为本地日历日期 `YYYY-MM-DD`，时间统一存储为 24 小时制 `HH:mm`，避免把无时区含义的课程时间错误转换为 UTC。

```ts
type RepeatRule = 'every' | 'odd' | 'even'

interface Period {
  number: number
  startTime: string
  endTime: string
}

interface Semester {
  id: string
  name: string
  startDate: string
  totalWeeks: number
  periods: Period[]
}

interface CourseSchedule {
  id: string
  dayOfWeek: 1 | 2 | 3 | 4 | 5 | 6 | 7
  startPeriod: number
  endPeriod: number
  startWeek: number
  endWeek: number
  repeat: RepeatRule
  classroom: string
}

interface Course {
  id: string
  name: string
  teacher: string
  color: string
  schedules: CourseSchedule[]
}

interface StoredScheduleData {
  schemaVersion: number
  semester: Semester | null
  courses: Course[]
  updatedAt: string
}
```

实体 ID 使用浏览器原生 `crypto.randomUUID()` 生成。课程与上课安排分别拥有 ID，保证编辑多个安排时能够稳定定位。颜色保存受控色值而不是任意 CSS 字符串，并由界面保证文字对比度。

## 7. 核心业务规则约定

### 7.1 教学周

- 每周从星期一开始，星期一至星期日构成一个教学周。
- 学期开始日期所在的这一周记为第 1 周，即使开始日期不是星期一。
- 当前日期所在周与第 1 周起始星期一的自然周差，加一后得到教学周编号。
- 日期早于第 1 周或晚于学期总周数时，界面显示“学期外”，但仍允许用户手动浏览有效教学周。

将“星期一作为一周开始”明确为 MVP 约定，避免计算逻辑受浏览器地区设置影响。

### 7.2 重复规则

一个安排在指定教学周显示，需要同时满足：

1. 教学周位于 `startWeek` 和 `endWeek` 之间。
2. `every` 每周生效，`odd` 仅在奇数教学周生效，`even` 仅在偶数教学周生效。

单双周始终依据教学周编号判断，不使用自然日历周编号。

### 7.3 冲突检测

两个安排构成冲突时必须同时满足：

- 星期相同。
- 节次范围存在交集。
- 周次范围存在至少一个共同教学周。
- 共同周中存在同时满足双方重复规则的教学周。

检测结果包含冲突课程和安排，供保存前提示。用户确认后仍可继续保存，符合产品设计中的“提示但不阻止”。

### 7.4 今日课程状态

今日课程先根据教学周和星期筛选，再按开始节次排序。课程的实际开始、结束时间从学期节次配置中读取：

- 当前时间早于开始时间：未开始。
- 当前时间处于开始和结束时间之间：进行中。
- 当前时间晚于结束时间：已结束。

业务函数接收显式的“当前时间”参数，测试中不直接依赖系统时钟。

## 8. 页面与路由

建议使用以下路由：

| 路由 | 页面 | 主要职责 |
| --- | --- | --- |
| `/` | 周课表页 | 展示网格、切换教学周、进入课程详情 |
| `/today` | 今日课程页 | 按时间显示当日课程及状态 |
| `/courses/new` | 新增课程页 | 新建课程及一个或多个安排 |
| `/courses/:courseId/edit` | 编辑课程页 | 修改或删除整门课程 |
| `/settings` | 学期设置页 | 设置学期和每日节次 |

应用启动后若没有有效学期配置，路由守卫将用户引导到 `/settings`。学期配置完成后再引导创建第一门课程。

课程编辑使用独立页面而不是复杂嵌套弹窗，以兼顾窄屏操作、浏览器返回行为和表单出错后的状态保留。删除和冲突确认可以使用弹窗。

## 9. 界面实现原则

### 9.1 周课表网格

- 桌面端使用 CSS Grid 构建“时间列 + 七个星期列”。
- 行高依据节次数量保持一致，跨节课程卡片通过网格行范围定位。
- 同一时间存在冲突课程时并排或错位展示，并添加明显的冲突标识。
- 当前日期列使用背景色或边框突出，但不只依赖颜色表达状态。
- 手机端允许网格横向滚动，并保持节次列可见；今日课程页作为更适合窄屏的快速入口。

### 9.2 样式与组件

MVP 使用原生 CSS 和 CSS Variables 定义颜色、间距、圆角及字体层级，不引入大型 CSS 框架。表单、按钮和弹窗可以自行实现少量基础组件；若实际开发中无障碍交互成本明显升高，再选用支持 Vue 3 的轻量无样式组件库。

所有表单控件必须有关联标签，键盘可以完成主要操作，颜色和文字对比度至少满足 WCAG AA 的常规文本要求。错误、冲突和课程状态不能只用颜色表达。

## 10. 本地存储方案

### 10.1 存储格式

- 使用固定键名，例如 `course-schedule:data`。
- 所有业务数据作为一个带 `schemaVersion` 的 JSON 文档保存。
- 首次启动时创建空数据；每次成功修改状态后整体写入。
- 写入前完成业务校验，写入后内存状态与持久化状态保持一致。
- 启动读取时执行格式校验，不能把未知 JSON 直接当作可信类型使用。

### 10.2 版本迁移与异常恢复

数据结构发生兼容性变化时递增 `schemaVersion`，并提供从上一版本迁移到下一版本的纯函数。应用启动时依次迁移，不允许页面组件自行兼容旧字段。

对于 JSON 损坏、浏览器拒绝存储或容量不足等情况：

- 不静默覆盖原数据。
- 在界面显示明确错误和恢复建议。
- 将解析失败的数据保留在内存中供用户复制，后续增加导出功能后可提供正式恢复入口。

虽然 MVP 使用 localStorage，但仓库接口应至少提供 `load`、`save` 和 `clear`，为以后替换 IndexedDB 或远程 API 留出边界。

## 11. 测试与质量保障

### 11.1 单元测试

使用 Vitest 重点覆盖高风险业务规则：

- 学期开始日处于一周中任意一天时，第 1 周计算正确。
- 学期前、学期中和学期后的教学周边界。
- 每周、单周和双周的显示判断。
- 一门课程多个安排的筛选与排序。
- 节次、周次和重复规则组合下的冲突检测。
- 跨中午、当天第一节、当天最后一节的课程状态。
- 存储数据解析、版本迁移和异常数据处理。

### 11.2 组件测试

使用 Vue Test Utils 验证：

- 课表卡片与空状态正确渲染。
- 表单校验、动态增删上课安排和错误提示。
- 删除二次确认和冲突确认流程。
- 页面状态变更后相关视图同步更新。

### 11.3 端到端测试

使用 Playwright 覆盖最关键的用户路径：

1. 新用户完成学期设置并创建第一门课程。
2. 创建每周、单周、双周和多安排课程，并在对应教学周显示。
3. 修改和删除课程后，周课表与今日课程一致。
4. 保存冲突课程时出现提示，并可确认继续。
5. 刷新页面和重新创建浏览器页面后，本地数据仍可恢复。

### 11.4 交付检查

工程建立后，每次交付至少运行：

```text
npm run lint
npm run typecheck
npm run test
npm run build
```

涉及关键用户流程或路由交互时追加运行 `npm run test:e2e`。CI 应执行同样检查，任一检查失败都不能交付。

## 12. 构建、部署与兼容性

Vite 生成纯静态文件，部署服务需要支持单页应用路由回退到 `index.html`。若托管环境无法配置回退，可改用哈希路由，避免刷新子页面时返回 404。

首版以当前两个主要版本的 Chrome、Edge、Firefox 和 Safari 为兼容目标。代码中避免依赖实验性浏览器 API，并通过自动化测试覆盖 Chromium；发布前对 Firefox、Safari 或其等价环境执行基础人工验证。

环境配置仅包含构建期公共配置，不能在前端包中放置密钥。应用不使用 `v-html` 渲染用户输入，课程名称、教师和教室始终按普通文本输出，降低本地持久化 XSS 风险。

## 13. 后续演进路径

### 13.1 数据导入导出与 IndexedDB

数据量增长、需要保存历史学期或导入文件时，可新增 IndexedDB 仓库实现。上层仍通过同一仓库接口访问，无需改写业务规则。

### 13.2 PWA 与离线能力

MVP 稳定后可加入 Web App Manifest 和 Service Worker，使静态资源离线可用并支持安装到桌面。提醒能力需要结合各平台通知限制单独评估，不能仅依赖 PWA 安装状态。

### 13.3 账号与云同步

需要跨设备同步时再建设 API、认证和服务端数据库。届时本地仓库可继续承担离线缓存，通过同步层处理版本和冲突，而不是让 Vue 组件直接请求远程接口。

### 13.4 手机 App 复用

领域模型和纯业务规则可以抽成独立 TypeScript 包，供基于 Web 技术的移动端方案复用。是否选择 Capacitor、React Native 或原生开发，应根据通知、桌面组件和平台体验需求另行决策，不在 Web MVP 中预设。

## 14. 建议实施顺序

1. 初始化 Vue 3、TypeScript、Vite、路由和测试工具。
2. 建立领域模型，并先用单元测试实现教学周、重复规则和冲突检测。
3. 实现数据仓库、版本化 localStorage 和应用级响应式状态。
4. 完成学期设置和课程编辑，打通首次使用流程。
5. 完成周课表与今日课程，并补齐组件及端到端测试。
6. 执行浏览器兼容性、响应式布局、无障碍和异常数据验证后发布 MVP。

## 15. 技术决策摘要

- 首版选择纯前端 Vue 3 单页应用，不建设后端。
- 使用 TypeScript 承载可测试、可复用的课程业务规则。
- 使用 CSS Grid 自主实现课表主体，避免被通用表格组件限制。
- 使用带版本号的 localStorage 文档，并通过仓库接口隔离存储实现。
- 使用 Composition API 管理当前规模的共享状态，暂不引入 Pinia。
- 以 Vitest、Vue Test Utils 和 Playwright 覆盖规则、组件与关键流程。
- PWA、IndexedDB、云同步和手机 App 均在出现明确需求后演进。
