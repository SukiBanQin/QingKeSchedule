## 二、iOS 行为基准

1. TODAY 的 ADD：没有课程时直接新建；已有课程时先进入选择页，可“新建一门课程”或复用
   已有课程资料只添加安排。TODAY 的 featured 与课程行点击进入整门课程编辑。
2. 新建课程默认名称／教师／教室为空，颜色 `#287B74`，一个当天、首节、1 至学期总周数、
   每周重复的安排。编辑保留课程和安排 ID；追加模式沿用名称、教师和颜色，只展示新增安排。
3. 课程信息含名称、可选教师、六个预设颜色和自定义颜色；每个安排含星期、起止节次、起止周、
   每周／单周／双周及可选教室。起止节次和周次相互校正，至少保留一个安排。
4. 保存顺序固定为基础校验、同课程新增完全重复检查、跨课程冲突评估。无效数据展示首条错误；
   冲突可返回修改或“仍然保存”。
5. dirty 时取消或返回必须确认放弃；编辑课程删除前必须确认。保存／删除成功后退出编辑页并在
   主壳短暂显示成功提示；持久化失败留在编辑页、保留草稿并显示错误。
6. 视觉使用方角终端表面、顶部取消／标题／保存栏、品牌头、编号表单分区和自定义确认层。
   Android 的系统返回、键盘和颜色选择使用 Android 对应方式，但安全区内结构、颜色、层级与
   文案应对齐 iOS。

## 三、Android 页面、状态与路由契约

### 3.1 ViewModel 是唯一编辑所有者

- 在 `ScheduleViewModel` 中新增可观察的 `CourseEditorState?`，并由私有 `CourseDraft` 驱动；
  不把路由、草稿、待保存课程或确认框只放在 Composable 的 `remember` 中。Activity 重建后编辑
  路由、全部输入、错误、冲突确认和 dirty 状态必须保留。
- `CourseEditorState` 至少包含路由模式（选择资料／新建／完整编辑／追加安排）、课程与安排快照、
  可见安排 ID、校验消息、确认提示、保存中状态和成功反馈。安排更新按稳定 draft ID，不用可变
  列表位置作为长期身份。
- 课程操作使用单一 in-flight 门禁。保存或删除进行中禁用重复提交、相关输入和退出动作；协程取消
  恢复可操作状态且不发布普通错误。状态保存失败时编辑页与草稿保留，关闭全局错误后回到原位置。
- `ScheduleAppState` 的课程写操作应返回明确成功／失败结果（或等价可测试结果），使 ViewModel
  只在 Room 已提交且新快照已发布后关闭编辑页。不得仅凭启动协程或按钮点击显示成功。

### 3.2 路由与入口

- TODAY 恢复一个真实 `ADD` 浮动操作：无课程直接打开新建；已有课程打开“新建／复用已有资料”
  选择页。选择页按名称稳定排序，但必须保留源课程身份，不能用可能重复的业务 ID 作为 Compose
  唯一 key。
- featured 与每个课程行点击打开对应源课程的完整编辑。成功保存或删除后回到原 TODAY 滚动上下文；
  主壳显示约 2.6 秒的非阻塞成功提示，连续操作以最新提示为准。
- 本轮周课表仍是壳层，不在其上放 ADD 或课程点击。等真实周课表实施时复用同一编辑路由。
- 编辑器采用主壳之上的全屏页面；系统返回和顶部取消调用同一退出逻辑。dirty 时显示放弃确认，
  未修改时直接返回；确认层显示时，系统返回只关闭确认层并继续编辑。

### 3.3 表单行为

- 非追加模式可编辑名称、教师和颜色；追加模式以只读资料卡展示原课程名称、教师和颜色，仅显示
  新增安排。追加模式保存整门候选课程，但不得改变原安排顺序或内容。
- 六个预设颜色保持 iOS 当前值。Android 自定义颜色使用方角 Compose 颜色对话框：颜色预览、
  RGB／HSV 可调控件和严格 `#RRGGBB` 输入共同指向同一候选色；不增加第三方依赖，不请求系统权限。
  非法十六进制值不进入 `CourseDraft.color`，保存仍由现有 `ScheduleValidator` 做最终校验。
- 选择开始节次超过结束节次时同步提高结束节次；结束节次低于开始节次时同步降低开始节次。
  起止周同理，并限制为 `1..semester.totalWeeks`。选择控件展示节次号及实际时间。
- “添加上课安排”复制最后一项的星期、节次、周次、单双周和教室，但生成新 ID；删除后至少一项。
  追加已有课程的初始新增安排仍使用 P2-03 已确认的当天／首节／整学期默认值，而不是复制旧安排。

## 四、保存、冲突、退出与删除

1. 点击保存先生成规范化候选并调用既有 `evaluateSave`。`Invalid` 只显示首条问题且不写 Room；
   完全重复沿用“该上课安排已存在，请勿重复添加”。
2. `Conflicting` 保存候选快照和冲突列表。提示中的课程名称去重并排序；共同周不超过 6 项时逐项列出，
   否则显示首周至末周。返回修改不写入；“仍然保存”只提交先前确认的候选，不重新读取已变化的表单。
3. `Ready` 或确认冲突后调用应用状态。成功必须等待事务提交和内存状态发布，再关闭页面并显示“课程
   添加成功／添加上课安排成功／课程修改已保存”。失败保持草稿、路由和 dirty，显示已有全局错误层。
4. 编辑模式才显示危险操作。删除确认后调用应用状态；成功发布删除后的快照、关闭编辑器并提示“课程
   删除成功”，失败保持页面。删除课程依赖既有 Room 级联，不单独逐条删除安排。
5. 保存、删除、冲突确认和快速双击均须防重复；取消确认、系统返回、Activity 重建和进程强停后的行为
   必须区分。内存草稿不承诺进程被系统杀死后恢复，已提交数据必须在重启后恢复。

## 五、已确认决定：重复课程 ID 的编辑目标

共享版本 1 导入和既有验证明确允许重复课程 ID。TODAY 展示已用 `OccurrenceKey(courseIndex,
scheduleIndex)` 保留每个来源项，但 iOS 与 Android 当前 `saveCourse/deleteCourse` 都按业务 ID 命中
第一项。若点击第二个同 ID 课程后直接复用现有方法，可能误改或误删第一项；iOS 当前源码也有此风险。
这属于已发现的基准疑似缺陷，不能静默照搬。用户已确认 Android 采用下方精确操作方案；
iOS 是否同步修复留待以后另行分析和授权。

可选方案：

1. **精确操作所选来源（已确认）**：Android 路由携带源课程位置与打开时指纹，状态／仓库新增按位置保存、
   删除能力；提交前核对目标仍匹配，失败则保留草稿并提示重试。导出业务 ID 不变，不收紧导入协议。
   这避免数据误改，但会暂时优于 iOS；是否另行同步修复 iOS 必须单独授权。
2. **严格照搬当前 iOS**：继续按 ID 操作第一项。跨端当前代码一致，但用户点击的课程可能不是实际被
   修改或删除的课程，不建议。
3. **检测到重复 ID 时阻止编辑／删除**：不误改数据，但有效导入数据会失去完整 CRUD，且与 iOS 行为
   不同，也不建议作为最终方案。

实施必须按已确认的第一种方案完成，不得回退到按 ID 命中第一项或阻止合法重复 ID 课程的 CRUD；
不得借此修改共享 schema、导入接受范围或 iOS 源码。
