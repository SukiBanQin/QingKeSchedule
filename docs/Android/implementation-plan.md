# 安卓分阶段实施计划

## 状态与执行原则

更新日期：2026-09-07。当前仅建立文档草案，安卓开发未开始。用户审阅文档后再指定实施任务，不把本文当成自动开发授权。

依据：[功能基线](product-baseline.md)、[技术方案](technical-design.md)、[交接状态](handoff.md)。阶段按依赖推进，一个阶段可以拆成多个有测试的提交；不为追求阶段整齐把全部改动压成一个提交。

## 阶段与交付条件

| 阶段 | 当前状态 | 范围与依赖 | 交付及验证 |
| --- | --- | --- | --- |

| P1 工程与规则 | 未开始 | P0 后确定包名和系统范围，建立 Kotlin／Compose 工程、固定依赖、定义领域及 JSON 数据类型 | 可构建启动；教学周、单双周、校验和共享 fixtures 测试通过 |
| P2 存储与状态 | 未开始 | 依赖 P1；事务存储、偏好设置、草稿和应用状态协调 | 增改删、顺序、写入失败回滚、重启与偏好持久化测试通过 |
| P3 核心页面 | 未开始 | 依赖 P2；首次使用、今日、周表、编辑、学期、教学日历、外观 | A01—A07、A11 的自动流程和同数据视觉对照；错误与确认分支可用 |

发现通知平台能力影响产品要求时及时回到 P0 更新差异，不等所有 UI 完成后才发现范围不可实现。未确认 D01 时不能扩展协议，未确认 D04 时不执行商店发布。

## 每次交给执行窗口的任务格式

```text
任务编号与阶段：
角色：执行；仅实施本次范围。
目标及对应 A 编号：
代码基准／当前分支：
必读文档与参考源码：
允许修改的路径：
已确认决定及不能自行决定的差异：
验收场景和需要运行的检查：
交付：修改摘要、相关测试及结果、提交编号、限制和下一步。
先检查 Git 状态，保留已有改动；完成后更新交接记录。
```

任务应覆盖一个能独立检查的结果，提供相关上下文，不反复复制整个聊天。执行窗口有疑问时，先核对文档与代码，再把影响范围的未决事项交回分析窗口。

## 人工协作流程

1. 分析窗口读取最新交接和实际代码，写出本阶段任务提示词；用户决定何时交给执行窗口。
2. Terra 实施、验证、更新记录并提交，返回摘要和提交编号。Luna 仅按需承担独立小任务，同一工作区不同时写入。
3. 用户把结果带回分析窗口；分析窗口审查实际 diff 和证据，记录问题或审查结论。
4. 执行窗口修正后重新验证；由用户确认产品验收，不用模型自述代替。
5. 切换官方／中转站前停止或完成正在运行的任务，保存交接；接手窗口先核对现场再继续。窗口名称不绑定服务配置，不承诺跨服务恢复旧会话。

## 防止状态失真

- “已实现”需要代码依据，“已验证”需要命令／设备与结果，“已审查”需要审查范围；三者不自动推出“用户已验收”。
- 文档所列命令不等于已经执行。失败、未运行、环境不具备分别记录。
- iOS 基准后续变更、发现缺陷、范围增减和协议决定应在功能清单及交接中同步更新。
