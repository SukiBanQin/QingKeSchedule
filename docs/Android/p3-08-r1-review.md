## 必须修正的问题

### 1. 已存在闹钟重提交失败时会从注册表消失

R1 改为每轮无条件重提交全部期望闹钟是正确方向，但 `active` 只保留本轮 `schedule` 成功的期望项，以及
「取消失败」的旧条目。若某条闹钟此前已经成功登记、注册表内容与期望完全相同，而本轮幂等重提交因瞬时平台
异常失败，该条目不属于 `stale`，会从下一版注册表删除；原系统闹钟却可能仍然存在。之后关闭提醒、删除课程或
修改时间时，协调器已经失去该闹钟的取消依据，形成平台孤儿闹钟，也与“单条失败保留并在下次重试”的设计冲突。

R2 应区分首次提交失败和既有活动项重提交失败：首次失败不写入；既有且未变化的条目重提交失败时保守保留，
下一轮继续重试；旧条目已经成功取消而新提交失败时不得保留；取消与提交同时失败时保留旧条目。补充覆盖上述
状态组合的 JVM 测试。`failed`、注册表、`activeAlarms`、`activeCount` 与 `degraded` 必须来自同一个最终活动集合。

同一问题还影响 `cancelAll` 的结果：取消失败条目已经保存在注册表中，但返回对象没有填充 `activeAlarms`，因此
`activeCount` 和 `degraded` 会错误报告为零／未降级。R2 应返回保存后的活动集合并增加取消失败断言。

### 2. 权限撤销设备用例没有真正按标题检查通知栏

`ReminderPermissionRevocationTest` 的无通知断言读取 `android.text`（正文），却与 `payload.title`（标题）比较，
所以即使目标通知真的出现，该查询通常仍返回空。`deliver()` 返回 `Suppressed` 的断言有效，但证据文档声称的
“通知栏中不存在该提醒标题”没有被这条代码证明。R2 应改查 `android.title` 或直接按完整 URI tag 定位，并在
预撤销 `POST_NOTIFICATIONS` 的专门运行中重新取证。常规已授权分支也应断言明确的可投递结果，避免其他抑制或
失败状态仍让测试通过。
