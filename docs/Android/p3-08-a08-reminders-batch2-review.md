## 必须修正的问题

### 用户授予通知能力后只刷新状态，没有重新安排提醒

用户在缺少 `POST_NOTIFICATIONS` 时打开提醒开关，UI 会同时保存开启偏好并弹出权限请求。保存后的第一次
`reconcile` 与系统弹窗并发：若协调器先读到权限仍未授予，它会得到空的期望集合，不登记任何闹钟。随后用户
点击允许，权限回调只调用 `refreshReminderStatus()`；该方法只读能力和注册表，不会重新协调。此时页面可能已经
显示「已授权／渠道可用」，但 `activeCount` 仍为 0，已有未来课程也不会产生提醒，直至 App 重建、再次修改偏好
或课表触发另一次协调。

从「系统通知设置」恢复 App 通知或提醒渠道时同样只依靠生命周期中的 `refreshReminderStatus()`，也存在相同
问题。现有设备流程测试在打开开关前预先授权；权限拒绝分支则直接调用 ViewModel，均未覆盖「先无权限开启 →
用户授权 → 无额外编辑」这条真实状态迁移。

R1 应增加明确的能力恢复入口：权限请求成功，或从系统通知／渠道／精确闹钟设置返回且提醒仍开启时，幂等执行
`reconcile` 并用结果更新 UI；权限仍拒绝时只刷新状态，不得自动再次弹窗。至少补充：

1. JVM 测试覆盖开启偏好已保存、首次协调因权限缺失无活动闹钟，能力恢复回调随后触发协调并更新活动集合；
2. API 37 设备测试从预撤销权限开始，在偏好开启后授予权限，不重启 App、不再次修改设置，验证注册表与
   AlarmManager 都登记了未来提醒；
3. 覆盖从系统通知／渠道设置返回的恢复路径，证明能力恢复后不只更新文字；保留拒绝权限不重复弹窗、课表继续
   可用的现有断言。
